# Findings: Tauri integration, storage, packaging, and release

## Official Tauri facilities to adopt

- Tauri v2 automatically merges `tauri.windows.conf.json` and `tauri.macos.conf.json` into the base configuration. The current macOS-only bundle settings should therefore be split instead of conditionally generated by custom scripts.
  - https://v2.tauri.app/reference/config/
- Use the official global-shortcut plugin for the guaranteed user-triggered capture command.
  - https://v2.tauri.app/plugin/global-shortcut/
  - https://github.com/tauri-apps/plugins-workspace
- Register Tauri's official single-instance plugin first, as its documentation requires, and use the second-instance callback only to reveal/focus the existing settings window.
  - https://v2.tauri.app/plugin/single-instance/
- A close-to-tray Windows agent must distinguish a user-originated `RunEvent::ExitRequested` from an explicit quit. The final implementation calls `prevent_exit()` for the former and shuts down native watchers only for the latter; this prevents a windowless process whose selection watchers were already torn down.
  - https://docs.rs/tauri/latest/tauri/enum.RunEvent.html
- Use Tauri's NSIS output first. Its default per-user installer does not require administrator privileges; WiX/MSI can be added later only for managed enterprise deployment.
  - https://v2.tauri.app/distribute/windows-installer/
- Use Tauri's Windows signing configuration for Authenticode signing and timestamping.
  - https://v2.tauri.app/distribute/sign/windows/
- Use the official updater plugin and signed updater artifacts. A GitHub-hosted static updater can publish `latest.json` with the signed installer artifact.
  - https://v2.tauri.app/plugin/updater/
- Use the official `tauri-action` workflow for Windows builds and GitHub Release artifacts.
  - https://github.com/tauri-apps/tauri-action

## Credential storage

- Replace direct macOS Keychain calls with `keyring-rs`, which provides a cross-platform API and a Windows Credential Manager backend.
  - https://github.com/open-source-cooperative/keyring-rs
- API keys should not be copied through settings JSON. A Windows user re-enters the key once; only non-secret preferences migrate through the existing settings layer.

## Configuration layout

- `tauri.conf.json`: shared product name, identifier, windows, CSP, capabilities, frontend/build settings.
- `tauri.macos.conf.json`: `.app`/`.dmg`, `.icns`, macOS minimum version, signing/notarization fields.
- `tauri.windows.conf.json`: `nsis`, `.ico`, WebView2 bootstrapper policy, Windows signing fields, updater artifacts.

## Initial Windows support policy

- Target Windows 10 22H2 and Windows 11, x64 first.
- Distribute a per-user NSIS installer so the application does not require elevation.
- Rely on the normal WebView2 bootstrapper policy, while documenting an offline/enterprise WebView2 option if beta evidence shows demand.
- Add ARM64 only after the x64 compatibility matrix passes; do not widen the first beta before the native capture layer is stable.

## Release gates

1. Clean Windows x64 build on GitHub Actions.
2. Installer works for a standard user and uninstalls cleanly.
3. All shipped binaries and updater artifacts are signed; signatures verify on a clean Windows VM.
4. Updater verifies the Tauri signature, upgrades forward, handles cancellation, and can roll back through an older installer.
5. Third-party notices record copied or adapted permissive-license code; GPL reference projects contribute no source code.

## 2026-08-12 CI verification update

- The maintained official action now documents `tauri-apps/tauri-action@v1`; older examples using `@v0` should not be copied into a new workflow.
  - https://github.com/tauri-apps/tauri-action
- Tauri's current GitHub pipeline guide says to set `projectPath` when the Tauri app is not at the repository root and links platform signing as a separate release concern.
  - https://v2.tauri.app/distribute/pipelines/github/
- The first checked-in workflow is deliberately a read-only push/PR gate: pinned Node/Rust versions, both Windows and macOS runners, renderer/accessibility tests, Rust checks/tests, and a no-bundle native build. Publishing, signing, updater JSON, and release write permissions remain excluded until the required signing identities and release endpoint exist.
- On this Windows host, Playwright completed every assertion but could hang while reclaiming a Vite server launched through nested `npm` processes. The repository now starts Vite as a direct Node child for UI checks, lets Playwright reuse it, and removes the owned child in a `finally` block; the full 51-test run exits cleanly with no listener left on port 4173.

## 2026-08-12 final local artifact

- The final Windows executable is PE x64 with the Windows GUI subsystem, so a release launch does not open a console window.
- The per-user NSIS installer is `Paper Float Translator_0.1.0_x64-setup.exe`, 3,303,636 bytes, SHA-256 `EF7DECA57747DED4042CC8D8E7914BA6A402BB8DD994DE1311DEE610B42A7BAA`.
- Both the application and installer are intentionally recorded as unsigned (`NotSigned`) until an Authenticode certificate and timestamping policy are supplied; a local build must not be represented as a public-release artifact.
